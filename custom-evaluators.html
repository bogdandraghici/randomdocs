Custom evaluators

Let users author their own eval judge — name, prompt, scoring — optionally starting from a built-in.

Status: Design prototype (frontend/designer scope). Custom evaluators live in memory only — no API, no persistence. Built-in evaluators still come from the backend unchanged, and no backend contract for authoring exists yet.

Main changes

  • The Eval Definitions tab was read-only. It now has a Custom section below the built-in category groups where users author their own evaluators.
  • Two entry points to create one: a New evaluator button in the tab header, and a dashed add-tile inside the Custom section.
  • A create/edit modal captures name, description, instructions (the judge prompt) and scoring.
  • Start from a template — an optional picker in the modal that prefills the whole form from any built-in evaluator, so users adjust rather than write from scratch.
  • Scoring matches the built-ins exactly: Numeric 0–1 with a pass threshold, or Binary pass/fail. No new scoring concepts.
  • Custom cards get a ⋮ menu — Details, Duplicate, Delete. Built-in cards are unchanged and stay read-only.
  • Custom evaluators appear in the evaluator picker when launching an experiment, so they can actually be run.

Behaviour

Where custom evaluators live

The Evaluators tab groups evaluators by category — General Quality, RAG, Code / Deterministic. Custom is a fourth group, always last.

The Custom section renders even when empty, so the feature is discoverable on a fresh workflow. Its empty state is a dashed New evaluator tile sized like a card.

Creating an evaluator from scratch

The modal asks for four things, in order: an optional template, a name, an optional description, and the instructions prompt — then the scoring.

The instructions field is the judge prompt sent to the model for every test-case output. It's a tall autosizing textarea, since these run long.

Starting from a template

Picking a built-in under Start from a template fills the form in one step: the name becomes <Built-in> (copy), and description, instructions and scoring are copied over. Everything stays editable.

Changing the template again re-fills the form. The picker only appears when creating — not when editing.

Choosing how it scores

A two-option segmented control sets the scoring mode:

  • Numeric 0–1 (default) — a Pass threshold field appears below, defaulting to 0.7. Outputs scoring below it count as a failure.
  • Binary pass/fail — the threshold field disappears; there's nothing to configure.

Editing, duplicating and deleting

Custom cards carry a ⋮ menu next to their type chip. Built-in cards don't.

  • Details — reopens the modal on that evaluator, with the template picker hidden.
  • Duplicate — opens a create modal prefilled from it, named <Name> (copy).
  • Delete — asks for confirmation first, then removes the card.

Running an experiment with one

Custom evaluators show up in the evaluator picker on Run New Experiment, grouped under a Custom heading alongside the built-in groups. From there they behave like any other evaluator — selectable, and their threshold is editable per experiment.

Edge cases

  • In-memory only — custom evaluators are lost on page refresh. Nothing is saved to a backend; this is the main prototype limitation.
  • Duplicate names are blocked — saving a name that matches any evaluator, built-in or custom, shows an inline error instead of saving. The check ignores case and the evaluator being edited.
  • Template prompts are mocked — the backend doesn't return instruction text for built-ins. Seven LLM-judge and RAG evaluators have hand-written prompts keyed by evaluator id; anything else gets one generated from its name, description and scoring mode. Real templates need a backend field.
  • Binary evaluators have no threshold — switching to Binary drops the field entirely, and a threshold chip never appears on the card.
  • Custom evaluators are never filtered out by node type — the experiment picker hides RAG evaluators for non-RAG nodes and Code evaluators for reply nodes, but the Custom group always shows. A custom evaluator that only makes sense for one node type is the author's responsibility.
  • Committed versions are read-only — on a committed application version the New evaluator button is disabled, the add-tile is hidden, and the ⋮ menu actions are disabled. This matches datasets and experiments.
  • Deleting doesn't rewrite history — experiments already scored with a custom evaluator keep their results; the confirmation dialog says so.
